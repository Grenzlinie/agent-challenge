# Design

## Context

比赛 B 要求在固定模型（GLM-5.3-Flash 320B-A18B，稀疏激活 MoE）与统一 A100 硬件、固定卡额度下做部署优化，评测题目为对选手完全可见的真实线上 query，赛期内可随时自测迭代。组织方提供标准化运行环境、官方参考部署与基线成绩。动机见 proposal.md，赛题要求见 specs/competition-b-llm-deploy/spec.md。

## Goals / Non-Goals

**Goals:**

- 跑通官方参考部署，复现基线成绩，建立自测—迭代闭环。
- 围绕响应指标系统优化：引擎与框架选型、MoE 并行（张量并行/专家并行）与调度、KV Cache 管理与连续批处理、Prefill–Decode 分离、量化与显存优化、服务化与容错。
- 产出可复现运行的提交物：服务镜像 + 启动/运行配置。

**Non-Goals:**

- 不改模型权重与任务语义（权重冻结，改动即违规）。
- 不在比赛算力池中提交非比赛任务。
- 详细评测口径以后继比赛章程为准，本设计不预设章程未公布的细节。

## Decisions

- **先复现官方基线再动手优化**：以官方参考部署与基线成绩为对照起点，所有改动都与基线对比响应指标。理由：赛题比的是「同样的模型、同样的硬件」下的相对提升；备选方案「直接上自研部署栈」被否，因为没有基线对照无法归因收益。
- **利用可见评测题高频迭代**：评测题完全对选手可见且可随时自测，因此迭代节奏以「改一处 → 自测一轮 → 记录指标」为单位。备选方案「攒一批改动再测」被否，因为无法定位单项改动对指标的影响。
- **质量与速度权衡显式记录**：针对 320B-A18B 的显存压力，量化等加速手段会在质量与速度间权衡，每次取舍都记录对响应指标的影响。理由：稀疏 MoE + 长上下文 + 高并发下，KV Cache 与显存管理直接决定性能。
- **规则允许范围内欢迎自研**：引擎/框架选型不预设唯一答案，候选方案逐一用同一批可见 query 对比后再定。

## Risks / Trade-offs

- 量化等加速手段损害输出质量 → 每次量化改动都同时记录质量与速度指标，权衡后再保留。
- 长上下文/高并发下 KV Cache 与显存管理不当导致不稳定 → 迭代中显式覆盖高并发与长上下文场景的自测。
- 比赛持续时间由组织方动态调整 → 关注群内通知与后继比赛章程，迭代成果随改随存，不依赖冲刺式提交。
