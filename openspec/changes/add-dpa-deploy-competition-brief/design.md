# Design

## Context

比赛 A 要求在固定软硬件条件下（同一 DPA4C 模型、固定 1024 原子周期体系、单张 PPU）做推理性能优化，组织方提供项目源码、官方基线与一键测试/提交工具。arena 算力池加入申请已获批，参赛环境可用。动机见 proposal.md，赛题要求见 specs/competition-a-dpa-deploy/spec.md。

## Goals / Non-Goals

**Goals:**

- 按官方流程（创建沙盒 → 跑通基线 → 找热点 → 修改源码 → Quick → Full → 提交）组织参赛工作。
- 以官方基线为对照，逐项验证改动的正确性与完整推理加速效果。
- 产出符合官方格式的提交包：源码 patch、测试结果、简短改动说明、复现镜像。

**Non-Goals:**

- 不训练、不改动 DPA4C 模型本身（权重与任务语义不属于本赛题范围）。
- 不重写已好用的 PyTorch 算子与厂商基础库。
- 具体技术边界以正式赛制为准，本设计不预设赛规未明确的边界。

## Decisions

- **从单个热点入手再扩展**：先在官方基线上做性能剖析定位热点（邻居/几何计算、CUDA kernel、原子力/维里量/应力计算等候选方向），从一个看得懂的小计算开始验证，再决定是否扩展到完整推理执行路径。理由：赛题明确允许从一个热点开始，且 Quick 流程支持快速迭代；备选方案「一次性改写多个环节」被否，因为正确性风险高、难以归因加速来源。
- **Quick 驱动迭代、Full 把关提交**：每次改动用 Quick 快速验证正确性与趋势，提交前必须用 Full 做完整性能自测。理由：这是官方给定的工具分工。
- **提交物由官方工具整理**：源码 patch 与测试结果优先用官方一键工具生成，复现镜像按官方指引另行 build。理由：赛题明确「具体提交格式以官方说明为准」，避免手工组装格式不符。

## Risks / Trade-offs

- 热点定位不准，优化收益小 → 先跑官方基线并剖析，以数据选热点，不凭直觉改代码。
- 改动破坏结果正确性 → 每次 Quick/Full 都先核对结果正确性，再看速度；正确性不通过不回退则不得提交。
- 正式赛制/提交格式后续才公布，与当前理解不一致 → 以正式赛制与官方说明为准，提交前复核一次官方指引。
