# Design

## Context

见 proposal.md 的动机。当前仓库只有两份待审邀请函摘要，没有已定稿 specs；邀请函的评测query完全可见被正式任务书的公开开发集与隐藏正式负载区分替代；排名落实为N@SLO、TPOT两级顺位。 正式任务书已通过 Playground CLI 下载文本，未下载权重和完整运行题包，本次没有运行比赛测试。

## Goals / Non-Goals

**Goals:** 固化正式赛制、来源链和可审核任务，保障实现仓库依据同一契约工作。

**Non-Goals:** 不在 store 存实现、权重、数据集、登录凭据；本次不创建收费服务，不把自测/上传状态包装成最终成绩。

## Decisions

1. 以开赛指南图片指定的任务 ID 下载的正式 task.md 为当前依据；邀请函保留作历史对照，不能替代正式评分规则。直接沿用旧摘要会遗漏已知约束，因此新增完整替代提案。
2. 沿用 `add-llm-deploy-competition-brief` 的 capability 路径，避免制造两个同题有效能力。团队 review 时选择本提案替代旧待审提案；禁止把冲突版本同时 archive。
3. 评分契约进入 specs，执行步骤进入 tasks，原文位置和哈希进入 sources.md。原始群消息、图片和题面留本地，仓库只提交所需摘要与引用。
4. 实现使用独立代码仓库；先验证资源和基线，再对照官方门禁优化。具体引擎/kernel方案须由基线证据决定，本提案不宣称已验证任何加速收益。

## Risks / Trade-offs

- [邀请函与正式题面冲突] → README明确正式口径，并保留差异来源。
- [旧提案仍可能被误用] → 在旧proposal顶部注明替代提案链接，归档前由团队统一选择。
- [本账号尚未完成资源认证] → 只记录CLI实际结果，不采用仓库内其他成员的approved陈述；离线规格工作继续。
- [题面可能更新] → 保存任务ID与文本SHA256，实施前重新比对。
- [完整运行材料尚未获取] → 本次仅承诺题面解读，完整题包、模型与环境检查作为后续前置任务。

## Migration Plan

通过自己的fork分支提交PR，由团队审查；不直接推上游或自行合并。需要撤回时revert文档提交。正式归档前消解与旧提案冲突，随后独立实现仓库按本规格执行。

## Open Questions

确定截止时间尚未在已读消息/题面中公布；继续关注组织方公告，不自定时间。
